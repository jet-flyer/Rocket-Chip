## Levels

CCSDS conformance is per book and per option (the PICS in Annex A of each Blue Book), not all-or-nothing of every clause. Cross-support is among matching profiles. Tick what you built. That matching-PICS reading is what Starcom means by “universal compatibility” — not every radio, and not every clause.

| Level | Means | PICS |
|-------|--------|------|
| **0** | Not implemented / out of scope. | No tick. |
| **Best effort** | A non-conformant approximation (COTS bearer, PIO bit pipe, LoRa, FSK continuous, serial FHSS). Labeled. Useful. | **Not a tick.** Still non-compliant for that book. |
| **Partial** | Part of the named book/option is implemented and tested (codec or encode side only, or a subset of procedures). The row says which part. | Not a tick for the whole book/option. Individual PICS items may be Y. |
| **Full** | Mandatory items for the scope named in the row are implemented and tested. Optional items ticked only if built. This is a scope claim, not formal compliance. | Maps to PICS items; not a signed PICS. |

**Rule of thumb** (not a hard red line): pursue Best effort only when it advances product performance or features, especially if the work later transfers to Full. Do not add it just to have it. Radio Best-effort on Rocket-Chip often stays RC-specific (pins, AO); keep those out of `starcom::ccsds`.

Honesty: a PIO bit pipe, RFM95 LoRa, bit-bang, or wrapping 211.2 inside LoRa packets is not 211.1 residual-carrier Bi-Phase-L PM. Wrapping 211.2 in LoRa does not buy dB (packet erasures). Code `PhyTier` maps `none` → 0, `best_effort` → Best effort, `compliant` → Full. Full 211.1 (`PhyTier::compliant`) is not offered.

## Annex A PICS: CCSDS 133.0-B-2 (Space Packet Protocol)

Draft and unsigned. Items, references and status flags are from 133.0-B-2 Annex A (A2.2, Tables A-1 to A-6), checked against the PDF on 2026-10-01. "Support" is Y / N / N/A as in A1.2. "Have any exceptions been required?" **No**, for the Starcom library: every mandatory Annex A item is implemented. The service-layer items (SPP-2, 6, 7, 8, 10, 11, 12, 13 and SPP-19 to SPP-22) are in `src/ccsds/space_packet_service.cpp`. That service layer is unit-tested only in Rocket-Chip's `test/test_space_packet_service.cpp`, not in the Starcom suite, and Rocket-Chip does not use it yet, because `src/starcom_adapt/byte_pump.cpp` packs with the PDU codec. This is a claim about the Starcom library, not about what Rocket-Chip sends on air. Source: `starcom/docs/audits/STARCOM_AUDIT_2026-10-29.md`, Section 3.

**Annex A status of the unsupported items.** Annex A marks the Octet String Service items (SPP-2, 6, 7, 8, 12, 13) and the Packet Assembly and Packet Extraction functions (SPP-19, SPP-21) M, with no condition attached in Tables A-1 to A-6. A2.1.4 NOTE: "A YES answer means that the implementation does not conform to the Recommended Standard. Non-supported mandatory capabilities are to be identified in the PICS". Starcom answers No as of 2026-10-29: the service layer is built and unit-tested (Rocket-Chip suite), not yet integrated.

**Packet-Service-only claim: what 133.0-B-2 says (checked against the PDF, 2026-10-01; facts only).**

- No clause permits claiming conformance for one service only. Annex A has no `O.n` rows and no condition tied to which service is claimed. The only conditions are C1 and C2 (Packet Secondary Header and User Data Field, Table A-4).
- Annex A marks these Octet String Service items M, unconditionally: SPP-2 Octet String SDU, SPP-6 Octet String, SPP-7 APID, SPP-8 Secondary Header Indicator, SPP-12 Octet_String.request, SPP-13 Octet_String.indication, SPP-19 Packet Assembly Function, SPP-21 Packet Extraction Function. SPP-9 Data Loss Indicator is the only optional (O) Octet String Service item.
- A1.1: "An implementation claiming conformance must satisfy the mandatory requirements referenced in the RL." A1.3: "If a mandatory requirement is not satisfied, exception information must be supplied by entering a reference Xi, where i is a unique identifier, to an accompanying rationale for the noncompliance." A2.1.4 NOTE: "A YES answer means that the implementation does not conform to the Recommended Standard."
- 1.3: "Where mandatory capabilities are clearly indicated in sections of the Recommended Standard, they must be implemented when this document is used as a basis for cross-support."
- Other text that bears on the question: 2.3.2 "Depending on the services provided by a real system, not all of the functions may be present in the protocol entity."; 4.2.1 and 4.3.1 "Depending on the services actually implemented within a real system" / "implemented by a real system", "not all of the functions may be present in the protocol entity"; 2.2.2.1 "Each source or destination SAP of an SPP service provider entity has an associated type of service, either Packet or Octet String. The service type need not be preserved from end to end of the managed data path; that is, asymmetric services may be provided."; Table 5-1 / SPP-26 "Service Type (this parameter is specified for each APID at the sending and receiving ends)", allowed values "Packet Service, Octet String Service".
- No CCSDS interpretation or Q&A on a partial-service claim was found (search not exhaustive).
- Status: closed 2026-10-01 on Nathan's full-compliance rule (project policy, not a standards finding): the Space Packet service layer implements every mandatory Annex A row (SPP-2, 6, 7, 8, 10, 11, 12, 13, 19-22; SPP-9 optional, skipped), so the one-service claim question does not arise. 211.0-B-6 EC1 2.2.2.2 (PDF text checked) says: "The packets have a Packet Version Number (PVN) authorized by CCSDS (see reference [H8]). These include CCSDS Space Packets and Encapsulation Packets." It has no "shall"; [H8] is the SANA registries, not 133.0-B-2; 133.0-B-2 is not cited in 211.0-B-6.

**Packet Sequence Count: what 133.0-B-2 says (checked against the PDF, 2026-10-01; facts only).**

- 4.1.3.4.3.3: "The Packet Sequence Count shall provide the sequential binary count of each Space Packet generated by the user application identified by the APID. Packet Sequence Counts are unique and independent per each user application as identified by the APID and are not shared across multiple APIDs."
- 4.1.3.4.3.4: "The Packet Sequence Count shall be continuous (modulo-16384). A re-setting of the Packet Sequence Count before reaching 16383 shall not take place unless it is unavoidable."
- 2.2.1 NOTE: "This protocol may be used for sending data from user A to user B and from user B to user A, but two separate managed data paths, one for each direction, should be used in such cases."
- 4.1.3.3.4.2: "The APID shall provide the naming mechanism for the managed data path."
- Green Book 130.3-G-1 (April 2023), 2.4.2 (Unidirectional (One-Way)): "Each managed data path only provides one-way transfer from a source user application to one or more destination user applications." and "In such cases, the managed data paths for sending telemetry are separate from the managed data paths for sending commands." Section 2.4.1: "it is a common practice for the destination user application to send back a confirmation to the source user application when it has received important data (such as commands) using another managed data path in the opposite direction." Section 2.5.3: "the instrument may use managed data path 3 to return to the control system an acknowledgment of receipt of each command it has received through managed data path 2".
- **Not addressed by 133.0-B-2:** the text does not say whether the count is scoped per (APID, direction) or per managed data path, and it does not address two distinct senders using one APID. (A statement about absence in the text, checked in 133.0-B-2 EC2 and 130.3-G-1; not a ruling on what the text requires.)
- Terminology: the terms "APID Qualifier", "Path ID" and "Path Identifier" do not appear in 133.0-B-2 or 130.3-G-1. They are in Issue 1 (133.0-B-1, September 2003, Historical): 2.1.3 "Each LDP is uniquely identified by a Path ID. A Path ID consists of an Application Process Identifier (APID) and an optional APID Qualifier." Issue 1 4.1.2.4.3.3 reads "The Packet Sequence Count shall provide the sequential binary count of each Space Packet generated by the user application identified by the APID." and does not contain the "unique and independent" sentence. Do not use these terms as 133.0-B-2 vocabulary. B-2 4.1.3.4.3.3 and 4.1.3.4.3.4 carry no wording of the form "incremented modulo 16384 for each Space Packet generated with the same APID".
- Status: decided (Nathan, Rocket Chip room, 2026-10-21). Each end keeps its own count on the shared APID 0x003. The station counts commands, and the vehicle counts ACKs in its `seq_cmd` lane. That's acceptable while the link is a single ground and vehicle pair. Revisit APID and count ownership when the network adds more nodes or repeaters. No CCSDS interpretation on two senders sharing one APID was found (search not exhaustive).

## Mission elapsed time field (legacy)

- **Pre-Starcom packets (`CcsdsEncoder`, APID 0x001 / 0x004):** the 4-octet secondary header holds `met_ms`, a big-endian unsigned 32-bit millisecond count. It has no P-field and no epoch, so it is **not** a CCSDS time code (CUC or CDS, CCSDS 301.0-B-4). It wraps at about 49.7 days. ACK packets carried a zeroed field.
- **Current Starcom packets:** no secondary header. `met_ms` is a 4-octet field at offset 40 of the 51-octet `TelemetryState` user data (little-endian, RP2350 native; only the Space Packet primary header is big-endian).
- **Meaning:** flag `kFlagsMetMission` set means `met_ms` is mission elapsed time, zero at T0 (the profile's `met_start_phase`, or plug-in when that is `kMetStartPlugIn`). Flag clear means time since vehicle boot, and the station must not present it as MET. `kFlagsMetDays` is a display hint only. Civil time rides separately in the `utc_*` bytes, valid only when `kFlagsUtcValid` is set. Sources: `telemetry_state.h`, `vehicle_met.h`, `ao_logger.cpp`.
- **Not claimed:** conformance to any CCSDS time code. TBD whether to adopt CUC or CDS in a future secondary header.

## Known gaps

- **On-air sequence count: implemented (doc corrected 2026-10-29).** `src/starcom_adapt/byte_pump.cpp` keeps a modulo-16384 count per APID, as 133.0-B-2 §4.1.3.4.3.3 and §4.1.3.4.3.4 require. `seq_nav` covers APID 0x001, and `seq_cmd` covers APID 0x003, which command and ACK packets share. `peek_tx_seq` reads the count, and `commit_tx_seq` advances it only after a successful encode.
- **Idle packet secondary-header flag.** `encodeSpacePacket` does not force the flag to 0 for APID 0x7FF (133.0-B-2 §4.1.3.3.3.4). Latent: nothing sends an idle packet today. It should be forced to 0.
- **Receive-side gap detection is in the adapter, not in Starcom.** `pump_note_rx_seq` (`byte_pump.cpp:325`, called from `ao_telemetry.cpp:1024`) adds (received − expected) mod 16384 to `rx_lost` for each APID. No Packet Loss Indicator (SPP-4, optional) is passed up as a service parameter, so SPP-4 stays N.

**Prox-1 randomizer: ANSWERED (quotes checked against the PDFs, 2026-10-01).**

1. Scope of the 131.0-B-6 mandate. 211.2-B-3 1.1: "The purpose of this Recommended Standard is to specify synchronization and channel coding schemes used with the Proximity-1 Data Link Protocol (reference [3]) and Physical Layer (reference [4])." 131.0-B-6 1.1: "...to specify synchronization and channel coding schemes used with the TM Space Data Link Protocol (reference [1]), the Advanced Orbiting Systems (AOS) Space Data Link Protocol (reference [2]), or the Unified Space Data Link Protocol (USLP) (reference [6])." The word "Proximity" does not occur in the 131.0-B-6 text (text search, 0 matches). 131.0-B-6 10.1: "The Pseudo-Randomizer defined in this section is mandatory to ensure sufficient randomness for all combinations of CCSDS-recommended modulation and coding schemes." Answer (Nathan, 2026-10-01): the 10.1 mandate is written for the links 131.0-B-6 1.1 names (TM, AOS, USLP), not for Proximity-1.
2. Coding options in 211.2-B-3. 3.4.2.2: "The C&S Sublayer shall generate the output stream of Proximity-1 coded symbols applying only one of the following coding options: a) no coding; b) convolutional code (see 3.4.3); c) LDPC code (see 3.4.4)." Note 1: "The convolutional and LDPC codes are optional. The use of the convolutional or LDPC code by the transmitter is configured using the Transmitter Data Encoding field of the SET TRANSMITTER PARAMETERS directive. The use by the receiver is configured using the Receiver Data Decoding field of the SET RECEIVER PARAMETERS directive." Annex A A2.2: items 3 (uncoded, 3.4), 4 (convolutional, 3.4.3), 5 (LDPC, 3.4.4, 3.4.5) are each "O.1", and "It is mandatory to support at least one of these items."
3. Randomizer text in 211.2-B-3 exists only for LDPC. 3.4.4.4: "The LDPC Codewords shall be randomized according to 3.4.5." 3.4.5.1: "Since the LDPC code is quasi-cyclic, the LDPC codewords require randomization in order to minimize the probability of false synchronization due to potential symbol slips. **Randomizer sequences: 131.0-B-6 Fig 10-2 and Fig 10-3, 231.0-B-4 6.2 (Duke read the PDFs; the 40-bit checks were re-run by the agent with Duke's reference script, 2026-10-01).**

- **131.0-B-6 Fig 10-2 (page 10-3), 131071-bit sequence, h(x) = x^17 + x^14 + 1 (10.4.1).** As Duke read the figure: 17 boxes X16 to X0, left to right, shift left to right, output taken from X0, feedback X14 XOR X0 into X16. Seed `11000111000111000` (10.4.3) loaded as written, leftmost character into X16, reproduces the first 40 bits printed in 10.4.3 NOTE 2: `0001 1100 0111 0001 1011 1001 0001 1011 1010 1001`. The reversed seed gives `1100 0111 0001 1100 ...` and fails. Period 131071 (script). The figure does not label which seed character goes to which box, and 10.5 says Figures 10-2 and 10-3 represent "possible generators": the taps, direction and output are fixed by the figure, and the seed-to-box mapping is pinned by the printed 40 bits.
- **Unit-test recipe (131071-bit).** Stages s[0..16] = X16..X0, s = the seed characters in order. Each step: output s[16]; fb = s[2] XOR s[16]; s = [fb] + s[0..15]. The test compares the first 40 output bits with the printed 40 bits and **must fail if they differ**. Handy extra check: the first 17 output bits equal the seed string reversed, `00011100011100011` (script). Negative test: the reversed seed must not reproduce the printed bits.
- **Legacy 255-bit sequence, Fig 10-3 (page 10-4), h(x) = x^8 + x^7 + x^5 + x^3 + 1 (10.4.2).** B-6 labels the stages X8..X1, shift left to right, output from X1, all-ones seed, feedback X8 XOR X6 XOR X4 XOR X1 into X8. First 40 bits `1111 1111 0100 1000 0000 1110 1100 0000 1001 1010` (10.4.3 NOTE 2), period 255 (script). **Implementer warning:** tapping the stages named by the polynomial exponents (X8, X7, X5, X3, X1) locks the register at all ones (recomputed). The taps follow the delay count from the output (the wire for x^k is k delays from the output). Among all non-empty subsets of the 8 stages, only {X8, X6, X4, X1} reproduces the printed bits (script search). Recipe: s[0..7] = X8..X1 all ones; output s[7]; fb = s[0] XOR s[2] XOR s[4] XOR s[7]; s = [fb] + s[0..6]. Fail if the first 40 bits differ.
- **231.0-B-4 6.2 (current; p.6-1, "6.2 RANDOMIZER DESCRIPTION"), h(x) = x^8 + x^6 + x^4 + x^3 + x^2 + x + 1.** B-4 6.2, Fig 6-1 (p.6-2) and 6.3.1 have the same text as the Historical 231.0-B-3 (checked against `231x0b4e1c1.pdf`, 2026-10-08). The Fig 6-1 wiring read below was done on the B-3 figure. "This sequence repeats after 255 bits"; first 40 bits `1111 1111 0011 1001 1001 1110 0101 1010 0110 1000`; Fig 6-1 "Initialize to an 'all ones' state" (stages X8..X1). 6.3.1: the BTG "shall be preset to the 'all-ones' state at the start of Transfer Frame(s)" (231.0-B-4 6.3.2, LDPC: "at the start of each codeword"). Test recipe (taps derived from the polynomial; the printed 40 bits are matched, Fig 6-1 on page 6-2 was viewed rendered (2026-10-01) and shows XOR (modulo-2) adders into stages X6, X4, X3, X2 and X1 plus the X1 output fed directly into X8; that wiring matches the polynomial, and the vector-drawing read of the same page (PyMuPDF: adders on the stage line after X7, X5, X4, X3, X2 plus the X1 output, fed into X8) gives the same taps, so the figure wiring is confirmed against the polynomial): s[0..7] = X8..X1 all ones; output s[7]; fb = s[1] XOR s[3] XOR s[4] XOR s[5] XOR s[6] XOR s[7]; s = [fb] + s[0..6]; period 255 (script). The 211.2-B-3 3.4.5.2.8 to 3.4.5.2.10 sequence has the same polynomial, the same 40 bits (Note 1) and an all-ones state at the start of each Codeword; its NOTE says "This is the same polynomial used in reference [E3]" ([E3] = 231.0-B-3).

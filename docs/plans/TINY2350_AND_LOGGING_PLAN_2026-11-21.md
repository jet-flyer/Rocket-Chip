# Phase 1 — Tiny 2350 bring-up on main (logging as-is)

## 1. Goal and scope

Nathan wants to see how the Pimoroni Tiny 2350 (PIM721, RP2350A, 4 MB flash, no PSRAM) runs the Rocket Chip (RC) main firmware as a **local-logging-only tracker** — an intended RC mode when there is no radio. Non-board-specific changes go in main. Board specifics stay in the board pack. Code stays hardware-agnostic (callers branch on pack constants, not board identity). No throwaway code and no quick hacks: root-cause fixes with host tests and bench. The Feather stays parked until everything else is stable.

**Why pivot now.** The scratch logger (`Rocket-Chip-tiny2350`, `tools/scratch/tiny2350_bringup/tiny2350_bringup.cpp`) did the first bring-up and is now a **bench harness only** — no new features. It has diverged from main (its own IMU config, trigger, recover policy, and flash page format). Its recover path is what produced the 3–4 s IMU holes after a Qwiic connector bump: any I2C error immediately runs an unconditional 9-clock bus recover and a full `imu_start()` (`tiny2350_bringup.cpp:573-601, 337-344`), and a failed init waits `kSensorRetryMs = 500` (`logger_config.h:90`) while polling is skipped (`tiny2350_bringup.cpp:613-614`). Unconditional 9-clocks can also NACK the barometer, and `baro_dps310_init` can stall 40 ms plus up to 50 × 10 ms (`baro_dps310.cpp:35-37, 115-139`). That is the recover policy, not the length of the bump. Main does not use that policy (section 4).

**In scope:** finish Tiny bring-up on main; shared I2C robustness; honest capability gates already started; logging as-is on this board (section 6); carry-in of parked shared fixes. The logging refactor is Phase 2 of this plan, not Phase 1. **Out of scope until Nathan says otherwise:** flashing or committing; Feather bench; inventing a Tiny-specific mission profile.

**Logging as-is is not a tracker.** Main only writes the RAM ring to flash when someone types the CLI flush command (`cmd_flush_log` → `flush_ring_to_flash` at `src/cli/rc_os_commands.cpp:1143` on this tree / `c542058b`; the only call in the Phase 0 worktree `Rocket-Chip-logevent-fix` is `:1144`). Nothing flushes automatically after landing. A power cut before that CLI flush loses the whole flight, and the SRAM ring overwrites after about 9 minutes (section 6). That is good enough for **bench bring-up**. It is **not** a working local-logging-only tracker until Phase 2 persist-to-flash lands (section 19.1, **DECIDED**, Nathan, 2026-11-22). The minimal Phase 1 auto-flush fork is closed (section 8).

## 4. I2C robustness (shared code)

**Bus speed.** Sensor I2C is set by one shared constant, `kI2cMasterFreqHz` in `src/drivers/i2c_master.h:24`, applied at `i2c_master.cpp:310`. Pins and the I2C instance are per-board (`board_tiny_2350.h:22-24`); **frequency is not**. Nathan (2026-11-21, about 4:15 PM CST) dropped the 100 vs 400 kHz A/B test and said this is the same bus as the main board. **Code check:** the constant is `kI2cMasterFreqHz = 400000` (UM10204 Fast Mode), which is 400 kHz, not 100 kHz. There is no per-board override (the Tiny pack has pins and instance only). The 100 kHz figure in the scratch `tools/scratch/i2c_bare_test/` harness is not what main uses.

**Observed faults (Buzz / bench, scratch logger).** Every observed I2C error came with handling. None have been seen at rest (the board was clean at rest for over 10 minutes). Across the lunch window (12:35–13:45, unwatched, America/Chicago), the IMU's resting X reading moved from 0.20 g to 0.09 g, so the breakout was nudged; the lunch errors very likely came from that nudge. A possible earlier bump as the cause of the original 3–5 error / ~8 recovery / 3–4 s hole is consistent with this. **Open:** isolation tests (cable middle / Tiny plug / breakout plug) to locate the contact.

**What main does today** (Core 1, `sensor_core1.cpp:5-6, 532-561`). Loop target 1 kHz (`kCore1TargetCycleUs = 1000`, `:42` as of 2026-11-23). A failed `icm20948_read` increments `imu_error_count` and clears `accel_valid` / `gyro_valid` (`:90-108, 154-156`). Each transfer's wall budget is 50 ms (`kI2cMasterDefaultTimeoutUs`, `i2c_master.h:25-29`) — sized for GlobalTop NMEA-over-I2C, not for the IMU. A finished NACK returns quickly; a stuck/stretch waits up to 50 ms, then ABORTs, and does 9 clocks only if SDA is still low and SCL is high (`i2c_master.cpp:549-559, 571-586`). After 10 consecutive fails, bus abort+reattach runs **only if the lines are not idle** (`sensor_core1.cpp:47, 101-107`). **There is no IMU device re-init** on this path (`:96-100`). There is no IMU give-up. `i2c_master_recover_bus()` (unconditional 9 clocks) is not on the vehicle IMU path. **The other line cites in this paragraph are from `c542058b`, before `732f8ea4` and `4622c90d`.**

**Worst-case outage, from those constants (not a bench measurement).** A few-ms NACK that leaves the lines idle: outage ≈ the glitch, at 1 ms cycles; no bus recover, no chip re-init. One hung transfer: ≤ 50 ms. Ten hung transfers: 10 × 50 ms = 500 ms, then abort+reattach if still not idle. If the chip needs bring-up to ACK again, main can keep failing indefinitely.

**Council (2026-11-21), section 8:** yes to this recover-policy shape (no unconditional 9-clocks on a finished NACK; device re-init only on stuck or high repeated-NACK; do not disturb the other bus occupant).

**Shared-code gaps**, now including Council item 2 (section 3.4):

1. An IMU re-init path, gated on a stuck line or a high repeated-NACK threshold — not on every finished NACK, and without unconditionally 9-clocking or re-initing the other occupant of the bus. Do not port the scratch `sensor_recover` policy. **Done 2026-11-23 (`4622c90d`, not yet benched):** see section 2. Thresholds: bus check every 10 failed reads (as before), re-init at 50 in a row with idle lines or at a check with stuck lines, at most one re-init per 1 s. A build check holds 50 reads × 2 transfers × the 2 ms IMU budget = 200 ms under 250 ms.
2. An IMU-specific transfer budget of about 2 ms, so a hung IMU read does not pay the 50 ms GPS-sized default (`kI2cMasterDefaultTimeoutUs`, `i2c_master.h:29`). **Done 2026-11-23 (`732f8ea4`):** the IMU now uses `kImuI2cTimeoutUs = 2000`, so ten hung IMU transfers cost about 20 ms (*estimate*) before the 10-fail check, not 500 ms. The "What main does today" paragraph above describes the code before that commit.
3. A flight-log / `LogEvent` record of bus errors and sample validity. Today `imu_error_count` is CLI/diag only (`rc_os_commands.cpp:377-386`). The log's `health_primary` is sampled at 10 Hz and written on the decimated fused frame (section 6); a short dropout can miss that window entirely. There is no `LogEventId` for I2C/IMU bus errors (`pcm_frame.h:44-53`). **Moved to Phase 2 (2026-11-23):** it changes the log format, so it goes with the Event record in the logging refactor (section 16).

## 6. Logging as-is

What main does today, from the constants on this tree / `c542058b` (not yet measured on the Tiny).

PSRAM, when present, is initialized in `main.cpp:235-238, 368-370` and passed into the logger at `:487-490`. The only functional consumer of that memory is the logger ring (`ao_logger.cpp:260-276`). CLI status and the boot banner only report it.

On the Tiny, `kPsramAvailable` is false, so `g_psramSize` stays 0 and `init_logging_ring` takes the SRAM path: a static 200 KiB buffer and decimation ratio 8 (`ao_logger.cpp:57-62, 74, 266-275`). The same SRAM path is what any no-PSRAM board gets.

Rate, from the constants:

- QP/C tick is 100 Hz (`lib/qep/bsp_qv.c:10, 50-53`, 10000 µs repeating timer).
- Logger timer is every 2 ticks = 50 Hz (`ao_logger.cpp:367, 385-386`).
- The box-car emits one frame per `ratio` inputs (`log_decimator`); SRAM ratio = 8 (`ao_logger.cpp:62, 275`).
- So the SRAM path is at most **6.25 frames/s** (50 / 8). The tick also returns early if the ESKF epoch has not advanced (`ao_logger.cpp:324-328`), so the rate can only be lower, not higher.

The CLI and the flight-log header still stamp 50 Hz (PSRAM) or 25 Hz (no PSRAM) (`rc_os_commands.cpp:727-729, 1126-1128`). Those numbers do not match the decimator.

Ring duration, arithmetic from the constants:

- Ring memory 200 × 1024 = 204800 B, minus a 16-byte `RingHeader` (`ring_buffer.h:22-28, 34`; `ring_buffer.cpp:39-40`).
- Frame size 61 B (`pcm_frame.h:80-89`).
- `max_frames` = (204800 − 16) / 61 = **3357** slots.
- At 6.25 Hz: 3357 / 6.25 = **537 s ≈ 8.95 min**, then `ring_push` overwrites the oldest frame (`ring_buffer.h:49`; `ring_buffer.cpp:62-66`).

The ring is written to flash only on the CLI flush. The only caller of `flush_ring_to_flash` is that command (`cmd_flush_log` at `rc_os_commands.cpp:1108`, the call at `:1143`; reached only from `ActionId::kFlushLog` in `cli_actions.cpp:190-191`). The same is true in Phase 0 (`rc_os_commands.cpp:1144`). There is no automatic write after flight-director LANDED, and no in-flight page program. Logging as-is is therefore **RAM-only**: if the board loses power before someone plugs it in and flushes, the whole flight is lost; after about 9 minutes (537 s at 6.25 Hz) the ring also overwrites the oldest frames. The on-disk log region, on a 4 MB part, is `kFlashLogStart` (512 KB) through `kFlashLogEnd` (`flash_layout.h:34, 59-62`). For `PICO_FLASH_SIZE_BYTES = 4 MiB` that end is `0x3F9000`, size 3,641,344 B — but today that region is not filled in flight. **Code check (Claude's review, verified 2026-11-21):** several other flash paths also have no arm or flight-phase guard: `cmd_flush_log` (`rc_os_commands.cpp:1108-1186`, dispatched from `cli_actions.cpp:190-191`); `AO_RCOS_start_erase_flights` (`ao_rcos.cpp:1227-1244`, only `AO_RCOS_cal_active()`); `cal_save_to_flash` / `AO_RCOS_start_cal_save` (`ao_rcos.cpp:346-367`, `:1277-1291`); and `save_wmm_position` → `calibration_save()` at `eskf_runner.cpp:326-331` (also `:280-283`, `:299`) on the first GPS 3D fix, with no phase test. CLI dispatch (`rc_os.cpp:438-461`) only skips keys while cal is active, not when phase ≠ IDLE. `docs/audits/AO_COMMANDMENTS_AUDIT_2026-04-27.md:41-46` (IV.2) and `standards/CODING_STANDARDS.md:115` claim mutating CLI is locked out off IDLE / gated by `test_mode_active()` and phase checks; that is not backed by code for these paths. Reachability while ARMED is a separate triage (field vs DEV_MODE desk); the missing guards are recorded here as a fact. **Nathan's decisions (2026-11-22):** the WMM in-flight save (`eskf_runner.cpp:326-331`) gets its own branch and PR — the fix is not trivial; persist is deferred until IDLE, with tests and a bench. CLI flush / erase / cal-save arm guards wait for refactor phase 5, with no interim fix (“no interim fix unless something is critically blocking, and even then the right way”).

This is adequate for **bench bring-up**. It is **not** a working logging-only tracker until Phase 2 persist-to-flash lands (section 19.1, **DECIDED**, Nathan, 2026-11-22). The minimal Phase 1 auto-flush fork is closed (section 8).

  1. **Code and boot memory stay write-protected.** ECSS-E-ST-70-41C PUS-C (15 April 2016), [PDF](https://ecss.nl/wp-content/uploads/2016/06/ECSS-E-ST-70-41C15April2016.pdf), ST[06] §5.4.3.3.1, §6.6.3.3.1, §6.6.6.2 (declared memory permissions and write protection). Protection is typically provided by intentionally enabling a write operation before modifying the software; at all other times, write operations are disabled." Duke could not open JPL D-17868 (WebFetch 403); those clause numbers are SWEHB's attribution and not independently verified.

  3. **Timing interference is bounded, not banned.** [EASA AMC 20-193](https://www.easa.europa.eu/sites/default/files/dfu/annex_i_to_ed_decision_2022-001-r_amc_20-193_use_of_multi-core_processors_mcps.pdf) (interference channels; MCP_Resource_Usage_3, MCP_Software_1).   4. **Power loss is limited and detectable.** GSFC 500-PG-8700.2.7B "Design of Space Flight FPGAs" §8.1 / §8.2 (effective 2012-08-13, **expired 2021-03-30**; guidance only), [PDF](https://soma.larc.nasa.gov/lws/pdf_files/3.17%20500-PG-8700%202%207%20B%20Admin%20Ext%202%20(2019-20)%20(1).pdf): hold-up to complete a write; detect corrupted writes; writing in flight is called "high risk" (radiation / high-voltage EEPROM rationale) but is not banned. ## 17. Rate policy, compression, and framing

### 17.1 Log-rate policy

**Source:** Goddard (`docs/reports/2026-11-21_goddard_log-storage-study.md`); Duke and Goddard both expect a rate policy to buy more flight time than the packing option in 17.2. Council item 6 asked for a coverage target first, noted ~11.6 min at full rate on 4 MB, and sketched phase-aware rates (full through main deploy plus a few seconds, then ~25 Hz IMU/fused, baro full rate throughout), with L1–L3 flights about 1.5–4 min trigger to landing.

**Nathan's decision (2026-11-21, about 3:27 PM CST, America/Chicago):** keep the log rate as it is today. No phase-aware rate change yet. A phase-aware policy becomes an option only after a true full-rate test can be compared against real rocket flight data. That option is gated on that comparison; it is not a Phase 1 or Phase 2 change.

**Code check** on the Council's ~11.6 min figure (arithmetic, not a measurement): the 4 MB log region is 3,641,344 B (`flash_layout.h:34, 59-62`). At the plan's ~20 pages/s × 256 B = 5,120 B/s, coverage is 711 s ≈ 11.85 min. The Council's ~11.6 min is that estimate, slightly rounded. Today's rate, from the constants, is at most 12.5 Hz fused on PSRAM and 6.25 Hz on SRAM (section 6; claim 2), not the raw+fused full-rate used in that 11.6 min *estimate*.

### 17.2 Delta predictor + bit-pack (two variants)

**Sources:** Goddard (study §3 options 3a/3b and §5 item 3); Duke (CCSDS 121.0-B-3, Blue Book, August 2020 — Duke verified on ccsds.org that this is the current issue). This is **one option with two variants**, not two tracks. Both run a delta predictor and then bit-pack. They differ in how the bit width is chosen.

- **Variant A — Blackbox-style fixed tags.** Like Betaflight/Cleanflight TAG8_4S16 / TAG2_3S32: a tag picks a width for a small group of values. The flash page boundary is where a full absolute sample restarts the deltas (a keyframe), so a torn page does not poison the next page.
- **Variant B — adaptive Rice (CCSDS 121.0-B-3).** Duke checked these clauses against his copy of 121.0-B-3 (August 2020):
  - §2.2: source coder = preprocessor + adaptive entropy coder, on blocks of J samples n bits wide.
  - §3.1: J ∈ {8, 16, 32, 64}, n ≤ 32.
  - §3.2–3.7: code options (fundamental sequence, split-sample, second extension, zero-block, no-compression) with per-block selection. Split-sample is the adaptive-width variant.
  - §4.2.5 and §4.4: unit-delay predictor and the signed-to-non-negative mapper.
  - §4.3: reference sample interval ≤ 4096 blocks, the analogue of a page restart.
  - §5.2: coded data set format, with the option ID key at §5.2.1.
  - Not needed: §5.3 (Space Packet wrapping) — that is a separate framing question (17.3).

**Default (section 10, constraint 5):** none in firmware yet. Format 3 already stores packed raw int16 (Goddard option 2), and that layout change alone takes IMU records from 21 B to 14 B.

**Synthetic numbers (Goddard, `docs/reports/2026-11-21_goddard_log-storage-study.md`; 60 s of made-up int16 at 225 Hz, not flight logs; the sim script is kept outside the repo).** Packed-float (option 1) is about **0.28×** vs raw packed int16 (~4.7 min of the study's 4 MB / ~2,500 B/s envelope). Delta + bit-pack without the leading flag (3a) is about 1.9× / 1.13× / 1.03×, or **28 / 17.8 / 16.4 min** still / moderate / harsh. With the flag (3b): about **2.2× / 1.2× / 1.09×**, or **31 / 18.9 / 17.2 min**. In the study's words, delta coding "halves the bench-still data but saves only about 3-18% in the vibration cases"; the recommendation still cites "about 10-20 % (synthetic estimate)" under vibrating flight data. The study's rate table treated DPS310 pressure and temperature as both 32 Hz; main runs temperature at 2 Hz (`baro_dps310.h:17`), which drops baro from about 192 B/s to about 102 B/s and changes the total by about 3%. LZ4, heatshrink, and deflate did worse on raw IMU under vibration and need more RAM (LZ4 default hash 16 KB; miniz deflate "~350 KB default; ~41 KB cut-down" — those RAM figures are from the study's sources, not measured here). Goddard recommends not using a general compressor for this IMU stream.

CPU % and on-device encode size for either variant are **to-be-measured** on the RP2350. Do not treat the synthetic ratios as a flight budget.

**Gate (refactor phase 7; Council item 6).** Compression is only for long missions (balloons, probes), and only after testing on a measured shake log. Existing logs are run offline, on the host, through both variants and compared to plain packed int16. Inputs include Buzz's shake log (speaker sweep, 150-400 Hz), a real v2 dump, and **Tiny as-is logs** (today's no-PSRAM 6.25 Hz path, once flushed) as one input. Add a variant as format 4 only if it wins by a margin set from that measured shake-log comparison (section 19.4, a refactor phase 7 test item), on a vibration/shake log, not on a still bench log. The per-page keyframe stays mandatory. LZ4, heatshrink and deflate stay out. Goddard will re-measure on real logs once they exist. A phase-aware rate under the parachute is not a Phase 1 or Phase 2 change (section 17.1).

**(a) Write log records as Space Packets, CCSDS 133.0-B-2, using the same APIDs as the radio side**, so one ground decoder could read a flash dump and the downlink. ### Goal

Offload a flight log over USB as a CFDP Class 1 (unacknowledged) file transfer with transaction closure. **Nathan's decision (2026-11-21, about 10:11 PM CST):** USB offload tries CFDP first and falls back to a raw dump on any issue. The board auto-erases only after a CFDP Finished reply with condition 'No error', delivery code Data Complete, and file status 'Delivered file retained in filestore successfully' (727.0-B-5 **Table 5-7**). After a raw dump, erase is a **manual** clear. **Duke** (2026-11-21): the board deletes only after a Finished reply whose file status is 'retained in filestore successfully' (he pointed at 727.0-B-5 Table 5-11). **Verified against 727.0-B-5:** that wording is in **Table 5-7** (Finished PDU Contents, §5.2.3), File Status value `'10'` — "Delivered file retained in filestore successfully." Table 5-11 in this issue is "Segment Request Form" (NAK segment offsets), not file status; Duke's table number is recorded as his pointer. The same Finished PDU also carries Condition Code (Table 5-5) and Delivery Code: `'0'` Data Complete "means that metadata, all file data, and EOF have been received, and the checksum has been verified" (Table 5-7, verified). The board-side rule is therefore: erase or delete the log only after Finished (complete) with condition 'No error', delivery code Data Complete, and file status 'retained in filestore successfully'. That is the same "no erase until a verified dump" rule as section 13 / 19.1, expressed as a CFDP close. Class 2 (acknowledged) is later, with the radio work. Design the log format and the offload path so Class 2 can use the same PDU, checksum, and filestore work. The implementation vehicle — a Starcom `cfdp` module, a port of a NASA engine, or the F´ component when we adopt F´ — is the open decision in the next subsection.

**Nathan/Duke, 2026-11-22:** The CFDP file checksum is an extra end-to-end check. It never replaces the per-page CRC-32 or the link's own CRCs (USB packet CRCs, CCSDS frame CRCs).

### Scope (727.0-B-5)

**Build now** (whatever vehicle is chosen)

- Class 1 — Unreliable Transfer, with the transaction-closure option so a Finished PDU closes the transfer. Duke pointed at §4.6.2–4.6.3 and §7 for this. **Verified in `cfdp.txt`:** §7 is "CFDP SERVICE CLASSES"; §7.1 defines Class 1 (Unreliable Transfer) and Class 2 (Reliable Transfer); §7.2 and Table 7-1 list the Class 1 source procedures. The unacknowledged-mode procedures, including closure, are §4.6.3: closure requires a duplex path (§4.6.3.1; restated in §7.2); the sender starts a Check timer after EOF (No error) and completes only when a Finished PDU arrives (§4.6.3.2); the destination issues Finished (complete) when reception is complete, with condition code "No error" only if the calculated and received checksums are equal (§4.6.3.3). USB serial is duplex, so closure is in scope. §4.6.2 in this issue is "OPTIONAL COPY FILE PROCEDURES AT THE RECEIVING ENTITY" (optional File-Segment-Recv / EOF-Recv indications), not the unacknowledged-mode procedures; that clause number is recorded as Duke's pointer, and the procedures we implement are the ones in §4.6.3 and Table 7-1.
- Shared PDU formats (section 5), CRC procedures (§4.1), and checksum procedures (§4.2, 32-bit file checksum accompanying the file) live with the Class 1 work so Class 2 can build on top.
- Filestore requests, including delete file, acted on when the transfer completes (§3.2.15, verified). The RC mapping is: do not erase the log region until a Finished (complete) PDU has been seen with condition 'No error', delivery code Data Complete, and file status 'retained in filestore successfully' (Table 5-7, verified; Duke pointed at Table 5-11). A delete-file request is how CFDP names that cleanup (offload, not storage).
- The optional closure-requested parameter (§3.2.22, verified) is how closure is requested for a Class 1 transaction.

**Later**

- Class 2 — Reliable Transfer, with the radio work. **Verified:** §4.6.4 is "ACKNOWLEDGED MODE PROCEDURES"; §4.6.4.1 requires a duplex path and is the start of NAK / ACK (EOF) / ACK (Finished) procedures. Do not implement §4.6.4 now, but do not paint the PDU and filestore APIs into a Class-1-only corner.

**Out of scope**

- Section 6 user operations (verified TOC and body: reserved CFDP messages, proxy, directory, remote status, remote suspend, remote resume).
- Annex B store-and-forward overlay operations (verified as a normative annex in the TOC and body).

CFDP is link-agnostic: it assumes a simple Unitdata Transfer (UT) layer and puts PDU length in the CFDP header so it does not depend on the underlying protocol (§2.2.5, verified). The Rocket Chip side only provides an adapter for USB serial plus a log-store-as-file mapping, both kept outside the protocol core.

**Closure-flag bug, 0x80 vs 0x40.** Goddard found that CF reads and writes the Metadata "closure requested" flag at the wrong bit. In `fsw/src/cf_codec.c:108`, `CF_CFDP_PduMd_CLOSURE_REQUESTED = CF_INIT_FIELD(1, 7)`, which is shift 7, mask **0x80** (the MSB). **Code check:** that define is at line 108 in the v7.0.2 tree (`CF_INIT_FIELD(1, 7)`; checksum type is `CF_INIT_FIELD(4, 0)` at line 109). **Verified against 727.0-B-5 Table 5-9 (Metadata PDU Contents, §5.2.5):** it lays out the first Metadata parameter octet as Reserved for future use (1 bit, set to '0'), Closure requested (1 bit), Reserved for future use (2 bits, set to all zeroes), Checksum type (4 bits). Closure requested is therefore the **second** bit, mask **0x40**, not 0x80. Effect (Goddard): a spec-correct sender that sets 0x40 is read by CF's R1 as closure not requested, so no Finished is sent; a closure request CF encodes sets the reserved bit. Goddard searched nasa/CF issues for this and found no existing report. F´ had the same bug and fixed it in [nasa/fprime#6136](https://github.com/nasa/fprime/issues/6136) (closed 2026-10-16; "Metadata PDU closure-requested flag uses bit 0x80 instead of 0x40").

**Missing PDU CRC and null checksum in CF.** Goddard, from the CF user-guide constraints (`docs/dox_src/cfs_cf.dox`): "The current version of CF does not support PDU CRC. The ground system needs to set the CRC Flag to false." Only the modular checksum is implemented (open issue nasa/CF#99: checksum-type field not checked). **Verified in Annex A:** the Class 1 sender ICS marks both as mandatory — CFDP-1S-06 "CRC procedures" (§4.1, status M) and CFDP-1S-25 "Null checksum algorithm implemented" (§4.2.2.4, status M). F´ likewise: Goddard, `PduHeader.cpp` "CRC not currently supported," and CRC-flagged PDUs are rejected.

**F´ v4.3.0, #6213 still open, #6136 fixed.** CfdpManager first shipped in **v4.3.0** (2026-08-20; also in v4.4.0, v4.4.1, and v4.4.2, not in v4.2.3 or earlier). Class 1 closure is still not supported in either direction (sender hardcodes closure off for Class 1; receiver has no R1 FIN entry). That remains open as [nasa/fprime#6213](https://github.com/nasa/fprime/issues/6213) (2026-10-16, low priority). The bit-position bug is the already-fixed #6136. Goddard also notes that [nasa/fprime#6377](https://github.com/nasa/fprime/issues/6377) saying "CF v7 fixes #6213" is incomplete: CF's state machine honors `close_req`, but because CF decodes the flag at 0x80, porting v7's logic without the #6136 bit fix would not interoperate with a spec-correct peer.

**Goddard's recommendation** (recorded as his, not adopted): write our own in Starcom and mirror nasa/CF's structure (codec / chunk-gap list / tx SM / rx SM / dispatch, and the same TxnState/SubState names), with cfdp-py (and LibreCube as a second option) as the ground peer and EmbeddedCFDP as an encoding cross-check. Reasons he gives: neither NASA engine gives working Class 1 closure today; both do POSIX file I/O inside the state machine, and Rocket Chip has no filesystem; a Starcom-native `read(offset, span)` maps onto the flash log and stays sans-I/O; house C++ standards are easier to meet by writing fresh; mirroring CF keeps a later F´ wrap or CfdpManager adoption easier. Porting CF would inherit the closure-bit bug, the missing PDU CRC and null checksum, and open issues #491 and #520. Adopting CfdpManager now needs the F´ framework and still lacks Class 1 closure.

**Class 1 plus Finished scope estimate** (Goddard): that scope is a *small subset* of the NASA engines — header, Metadata, File Data, EOF and Finished codecs, the modular checksum (plus null and the PDU CRC-16 if we want honest Annex A ICS coverage), and two small state machines with a Check timer. Most of CF's 12,718-line engine and F´'s ~11k-line engine-plus-codec are Class 2, channels, playback, polling, history, and commands. See also the Size subsection.

**Standards, in short.** nasa/CF meets GSFC / cFS C conventions; CfdpManager meets F´ C++ conventions and the F´ no-dynamic-memory-after-init practice. Neither is written to Starcom's bar in `starcom/docs/WORKING_HERE.md` (sans-I/O portable core, no Rocket Chip types, no exceptions / RTTI and no `new` on codec paths, house camelBack) plus Rocket-Chip `standards/CODING_STANDARDS.md`. Reuse therefore either keeps the upstream style behind a sharp boundary (a cFS app, or an F´ component when we are on F´) or pays a port into `starcom::cfdp`. Licenses are not the blocker: both NASA trees are Apache-2.0, which matches Starcom's current Apache lean (`starcom/LICENSE` is still a placeholder) and is compatible with the GPL-3.0-or-later Rocket Chip tree if we link later.

**Options** (no order of preference; Goddard's recommendation is option 1, plus mirroring CF's structure)

1. **Write our own in Starcom** — a `starcom::cfdp` module, no heap after init, no RC types, Starcom coding standards. Matches the existing whiteboard want (`starcom/AGENT_WHITEBOARD.md:113`: own stack module above `starcom::ccsds`). Full control of Class 1 closure and of a log-store-as-file mapping. Cost is a large new protocol entity (see Size).
2. **Use nasa/CF as a cFS application** — bring cFE / OSAL / the software bus along, or write a large shim. Not a practical fit for the current Starcom / Rocket Chip tree.
3. **Port or extract the CF v7 engine into Starcom** — start from the current `dev` engine (better Class 1 closure than the F´ v3.0.0 port), isolate it from cFE / OSAL / SB (the SB split is incomplete), add the missing Tx-side closure-request API, and replace OSAL file I/O with a filestore callback that can point at the log region. This is a real port, not a copy: thousands of lines, plus a Starcom UT / buffer / tick wrapper, plus a style and language (C vs house C++) decision. CF remains the state-machine reference even if we do not port it.
4. **Reuse F´ `CfdpManager` when we adopt F´** — the natural path if CFDP can wait on, or move with, the near-future F´ project. It cannot be dropped into the Starcom core today without taking the F´ framework with it. Class 1 closure would have to be added (or taken from a CF v7 realignment, issue #6377), because the present component does not fulfill a Class 1 closure request and our USB offload needs that Finished / checksum close. Adopting F´ *now* just to get CFDP would be a much larger scope change than a Starcom module or a CF port.
5. **EmbeddedCFDP as a codec only** — possible PDU / checksum / CRC starting point or cross-check; not a full Class 1 entity with closure. Repo is new.
6. **cfdp-py** — ground and host-test interop only.

Goddard's assessment is in; the vehicle decision remains open until implementation time (Open questions (d)). Do not start a large write or a large port until Nathan decides. Public API sketch for a Starcom core (names are indicative; house camelBack when written):

- A sans-I/O entity (source and destination, or one entity that can play either role): `put` a file (source name, destination name, closure requested, optional filestore requests); `onUtPdu` to accept a complete PDU; `tick(now)` for the Check timer; outgoing complete PDUs taken by the caller; events for Notice of Completion, faults (including Check Limit Reached), and filestore actions.
- PDU encode/decode and the file checksum as plain functions on caller-provided spans. No heap after init, no `new` on those paths.
- A narrow UT callback or byte-span interface only — not a socket, not USB, not flash.

The core may use `starcom::ccsds` Space Packet helpers when a PDU is carried in Space Packet user data; it must not assume an RC frame type.

**If we adopt F´ `CfdpManager`**, the layout is an F´ component with F´ ports, not `starcom::cfdp`. The Rocket Chip (or later F´) USB UT adapter and the log-store-as-file mapping still sit outside the protocol engine. Class 1 closure has to be present before that path can satisfy the no-erase-until-Finished rule.

### Adapter boundary

CFDP does not know about USB or flash (§2.2.5). Rocket Chip, outside the protocol core, provides:

1. A USB-serial UT adapter: delimit and deliver complete CFDP PDUs (and, if used, the Space Packet wrapper) in both directions. Closure needs the return path (§4.6.3.1).
2. A log-store-as-file mapping: present the current flight log as the file being Put, and honor a verified delete-file request only after Finished (complete) with condition code 'No error', delivery code Data Complete, and file status 'retained in filestore successfully' (Table 5-7, verified). That is the no-erase-until-verified-dump rule. Erase remains an Idle-only operation in the logger (section 13). nasa/CF's OSAL file calls, and F´ file or `fileIn` ports, would have to be wired to this mapping rather than to a POSIX path on the flight part.

Board pins, CLI, and mission profile stay in Rocket Chip.

**(b) What happens when a Class 1 checksum fails?** (Nathan asked; **Duke's answer**, 2026-11-21, about 4:38 PM CST; clauses verified against 727.0-B-5 as noted). A checksum mismatch at the receiver declares a File Checksum Failure fault (§4.6.1.2.8 d, verified; condition code 'File checksum failure', Table 5-5 '0101', verified). The book says the action taken need not discard the delivered file; the default handler for that fault may be Ignore, which announces the discrepancy in a Fault.indication but still permits completion of the Copy File procedure at the receiving entity, and notes that this setting might be especially appropriate for unacknowledged mode (NOTE under §4.6.1.2.8, verified). Handlers are selected from the MIB or a per-transaction override and are cancel, suspend (limited), ignore, or abandon (§4.8.1–4.8.2, §3.2.12, verified). Filestore requests, including delete, are executed only if the associated Copy File procedure completed with no error; a fault means they are not executed (§4.9.1, verified).

Duke: the default handler can flag the bad copy and keep it; with closure, the Finished reply reports the failure, so the board keeps the log, and a retry is a new transaction started by a person or a script. **Verified around the Finished reply:** transaction closure is described in §2.4 (optional Finished PDU in unacknowledged mode, so the source can be informed of the outcome) and the procedures are §4.6.3 (both verified). Receipt of a Finished PDU at the sender causes a Notice of Completion, Completed or Canceled depending on the nature of that PDU (§4.6.3.2.3, verified). If the handler issues a Notice of Cancellation, and the transfer is unacknowledged with the Closure Requested flag set, the receiving entity shall issue a Finished (cancel) PDU whose condition code is the fault that triggered cancellation (§4.11.2.3.3, verified). That is how the Finished reply reports File Checksum Failure when the handler is cancel. The Ignore path is the one that can keep the (bad) copy at the receiver; it does not, by itself, require a Finished (complete) PDU to carry 'File checksum failure' — §4.6.3.3 a) issues Finished (complete) only when reception is deemed complete per §4.6.1.2.8, with condition 'No error' if the checksums were equal or 'Unsupported checksum type' otherwise (the null-checksum complete path in §4.6.1.2.8 c). The board-side rule already in this section (erase only after Finished (complete) with condition 'No error', delivery code Data Complete, and file status 'retained in filestore successfully', Table 5-7) is how the flight log is kept on the vehicle. The book does not define an automatic Class 1 retransmission of the file; Duke's retry — a new transaction started by a person or a script — is the answer for that.
